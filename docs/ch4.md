sys_get_time
这个说在赋值时可能会跨页
用translated_byte_buffer 这个把虚拟内存变成切片

可以举一个具体例子。

`TimeVal` 里面有两个 `usize` 字段：

```rust
pub struct TimeVal {
    pub sec: usize,
    pub usec: usize,
}
```

在 64 位平台上，一个 `usize` 是 8 字节，所以整个 `TimeVal` 是 16 字节。

假设页大小是 4096 字节，用户传进来的 `_ts` 是 `0x12ff8`。

- 当前页范围是 `0x12000..0x13000`
- 下一页范围是 `0x13000..0x14000`

那么 `TimeVal` 的 16 个字节就会落在两页里：

- `0x12ff8..0x13000` 在第一页，一共 8 字节
- `0x13000..0x13008` 在第二页，一共 8 字节

也就是说：

- 前 8 字节可以写入 `sec`
- 后 8 字节要写入下一页中的 `usec`

所以这里不能假设 `_ts` 对应的是一段连续的物理内存。虽然虚拟地址看起来是连续的，但是翻译到物理页之后，很可能被分成两段。

`translated_byte_buffer(current_user_token(), _ts as *const u8, size_of::<TimeVal>())`
做的事情就是：

- 根据当前进程的页表，把用户虚拟地址翻译出来
- 如果这一段内存跨页，就拆成多个切片
- 最后返回一个 `Vec<&mut [u8]>`

上面这个例子里，它大概会返回两段：

```rust
vec![
    &mut [第一页剩下的 8 字节],
    &mut [第二页开头的 8 字节],
]
```

然后内核把 `time_val` 先看成一个 16 字节的字节数组，再分段拷贝过去。

如果直接赋值，比如想写成：

```rust
unsafe {
    *_ts = time_val;
}
```

会有几个问题，首先就是运行得时候会通不过，具体可以看输出得信息。

第一，`_ts` 是用户地址，不是内核已经确认可直接访问的内核地址。内核不能只因为拿到了一个指针，就默认它一定合法。

第二，`_ts` 可能跨页。直接做结构体赋值时，编译器会把它当成对一段连续目标内存的写入；但这段连续虚拟地址背后对应的物理页需要通过用户页表一页一页翻译，不能跳过这个过程。

第三，如果后一页没有映射，或者权限不对，那么写到一半时就可能触发异常。这样不仅系统调用失败，还可能把前一半数据已经写进去了，留下一个只写了一半的 `TimeVal`。

第四，就算两页都映射了，直接解引用用户指针这种写法也绕过了内核对用户内存访问的统一处理方式，不符合这里实现系统调用时的安全模型。

所以更稳妥的做法就是：先把用户虚拟地址翻译成内核可操作的若干切片，再逐段拷贝。这样无论是否跨页，处理方式都是一致的。
